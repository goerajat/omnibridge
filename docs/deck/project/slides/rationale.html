Six design decisions, each made for a measured reason

One spinning thread per loop

A blocking read pays a 5 to 20 µs kernel wake-up that varies run to run. Spinning removes it. The price is one core per loop.

Pinned to an isolated core

Ticks, interrupts and other threads are moved off the core at boot. Little at the median, a lot at the tail, and it makes runs comparable.

Flyweights over direct buffers

A message is a view over the bytes where they arrived; fields are read and encoded in place. No parse tree, no copies, no objects.

Lock-free ring per connection

Any thread claims, encodes and commits; the loop drains to the socket. A commit from the loop thread is written at once.

Zero allocation, enforced by tests

A test asserts 0 bytes per order on the acceptor with the journal on, and at most 320 on the simulator. GC is a non-event.

Journal first, on the critical path

Durability before the send was never traded away. The work went into making the write cheap: 0.4 to 0.8 µs, page faults taken ahead.

Also: HOCON configuration with a component lifecycle (initialize, active, standby, stop), so latency-sensitive deployments can switch off admin, persistence or the scheduler

These are the reasons the engine is shaped the way it is. Each one was chosen against a measurement rather than a preference. The first two are about the host and are where the tail latency went. The middle two are about memory and are where the median went. The last two are the principles that were not negotiable: no garbage, and no send before the journal.
