Monitoring: engine metrics in Prometheus, Grafana dashboards and alerts, OmniView for operators

Metrics, from the engine

A Prometheus endpoint on each admin port: session state, logons, messages in, out and rejected, sequence gaps and resends, heartbeats, ring-buffer claim failures, journal writes, JVM.

Meters resolved once; nothing built per message.

Grafana and Alertmanager

Three dashboards shipped: Overview, Session Deep Dive, and JVM and Infrastructure. Fifteen alert rules; critical ones page, warnings go to chat.

Thirty-day retention, five-second scrape.

OmniView console

One web console across all engines: session health cards, live state over WebSocket, enable or disable a session, set sequence numbers, act on simulator orders, browse the Aeron stores.

A chat page queries sessions through the MCP server.

Critical alerts

Session disconnected, all sessions down, heartbeat timeout, ring-buffer claim failures, high reject rate, processing latency, GC pause. Warnings: logon failure spike, throughput drop, sequence gap, heap and direct-buffer pressure.

infrastructure/docker for the local stack (Prometheus 9090, Grafana 3001, Alertmanager 9093); the AWS monitoring host runs the same stack plus OmniView on 3000

Operations get three things. Metrics from inside the engine, exposed in Prometheus format without touching the hot path. Dashboards and alerts that come with the product, so a deployment is observable on day one. And OmniView, a console that shows every engine's sessions in one place and lets an operator act: enable, disable, set a sequence number, or look at an order in the simulator.
