What is next: the remaining microseconds are in the TCP stack and the host, not the engine

A purpose-built TCP for the bypass path

F-Stack's FreeBSD TCP costs ≈ 3 to 5.5 µs one way (6 to 11 per round trip). Published from-scratch stacks run at a few hundred nanoseconds per packet. A minimal single-connection stack is the largest software win left: up to ≈ 4.5 µs one way on c6in.

Metal with the fast card, repeated

One AMD metal stack gave ≈ 13.8 µs one way (27.6 round trip). A c6in.metal run would separate the hypervisor's share from the card generation's on the Intel path; both are an afternoon and under $30.

Write-combining for the NIC's low-latency queue

The kernel driver uses it; the DPDK path never did because the stock vfio driver has none. Enabling it would move every bypass row down together.

Hardening the bypass path for production

Graceful stack shutdown, running without root, TLS on the bypass transport, and the alert and dashboard metric names reconciled with what the engine emits.

Everything above is optional for a kernel-path deployment, which is production-ready today at ≈ 23 µs one way (45 round trip) on a cloud VM and ≈ 17 to 19 (34 to 38) on metal

The engine's own share is four to seven microseconds and tracks the clock, so the next gains are elsewhere. The biggest is a TCP stack written for one connection on a reliable link, which the literature says runs an order of magnitude cheaper than FreeBSD's. The rest is host work and the production hardening a bypass deployment needs.
