Omni-Bridge is an exchange connectivity engine written in Java. This deck covers what it does, how it is built and why, how it is deployed and monitored, and the latency programme that took the order round trip from 280 microseconds to under 28 on AWS, about 14 one way, including what we tried and discarded along the way.

One engine between your applications and the exchanges, built so it is never the slow part

Connectivity

Initiator and acceptor sessions for FIX, OUCH and three binary exchange protocols; logon, heartbeats, sequence recovery and resend handled by the engine. The next protocol is a module.

Latency by design

A single busy-spinning thread per event loop, flyweight messages over direct buffers, lock-free ring buffers, and zero bytes allocated per message, enforced by tests.

Durable sessions

Every message journaled before it is sent, on Chronicle Queue, a memory-mapped log, and optionally copied over Aeron, a UDP messaging library, to another host. Resend and restart recover from the log.

Operable

Admin REST and WebSocket API, Prometheus metrics with Grafana dashboards and alerts, and OmniView, a web console for session health and control across every engine.

Java 25

Plain JVM, no custom runtime. HOCON configuration, components with a managed lifecycle and active/standby states, a multi-protocol exchange simulator, and a kernel-bypass transport (the network card driven from the engine's own thread, no operating system in the data path) as a switch.

Maven multi-module project; engines, persistence, admin, metrics and tooling are separate modules

Omni-Bridge is an exchange connectivity engine. It handles the session layer of the venue protocols so applications only deal with orders and executions. It is written to be fast by construction rather than tuned afterwards, it journals everything, and it ships with the monitoring and console that operations teams need.

Where it fits

When the venue's matching engine is in the cloud, the region is the colocation

Crypto spot and derivatives

Coinbase runs its US spot exchange in AWS us-east-1 and tells FIX clients to deploy there; Binance's FIX endpoints sit in AWS Tokyo. Kraken: about 200 µs over a cross-connect, about 2 ms from AWS London.

Prediction markets

Kalshi offers FIX order entry with AWS PrivateLink into its environment. Market making there is dozens of sessions across markets and sub-accounts on one box, run from an admin API.

Cloud-native regulated venues

Aquis runs its equities exchange on AWS; Nasdaq moved MRX and GEMX onto AWS Outposts in its own data centre. The matching engine is becoming a cloud tenant, and the firms connecting to it follow.

What the engine buys there

Tails, not medians. Inside a region the fabric is tens to hundreds of µs; what matters is that a GC pause or page fault never becomes a 2 ms stale quote.

Durability without a trade-off. Every message journaled before it leaves and copied to another host, at no cost to the round trip.

Many sessions, few cores. One loop thread serves many sessions on one port, with metrics, alerts and a console.

A test rig that matches production. The simulator and the scripted AWS run measure a firm's own stack before it pays for a cross-connect.

Not the target: latency-sensitive trading on CME, Eurex, NYSE or Nasdaq's classic books stays in Aurora, Frankfurt, Mahwah and Carteret on overclocked hosts with FPGA cards. There the engine competes on its kernel path; the AWS numbers show the engineering, not the deployment.

Sources: Coinbase Exchange systems operations; Kraken colocation guide; Kalshi FIX connectivity; Glassnode latency monitor (Binance); Aquis on AWS

The question every buyer asks: why a low-latency FIX engine in the cloud when the fast money sits in a cage next to the exchange? Because a growing set of venues have their matching engine in a cloud region: most crypto exchanges, the prediction markets, and now some regulated equities venues. For those, the region is the colocation, and the firm's own engine is the part it controls. The engine's contribution there is less its median than its tail, its durability and the number of sessions one box can run. For CME, Eurex or the NYSE this is a conventional kernel-path FIX engine with an unusually well-measured tail, not a colocation replacement.

The four technologies the engine builds on, in plain terms

Journal

Chronicle Queue

An open-source Java library that appends records to a memory-mapped file. A write is a memory copy; the operating system flushes the page to disk. It is the engine's per-session journal.

Replication

Aeron

An open-source low-latency messaging library. It sends over UDP with its own reliability and flow control, from a media driver on a separate thread. The engine uses it to copy each journal entry to another host.

Kernel bypass

DPDK

The Data Plane Development Kit: libraries that let a user-space program own a network card and poll it directly, skipping the kernel's network stack and its interrupts. It moves raw packets and has no TCP of its own.

TCP on bypass

F-Stack

FreeBSD's TCP/IP stack packaged as a library on top of DPDK, giving a program sockets on a card the kernel never touches. The engine's optional bypass transport runs it on its own pinned thread.

Also in this deck

SBE, Simple Binary Encoding, the FIX community's binary codec behind iLink 3 and Optiq. SoupBinTCP, Nasdaq's framing and sequencing layer under OUCH. HOCON, a typed configuration format. FFM, Java's foreign function interface, which calls C code without JNI.

Licences: Chronicle Queue and Aeron are Apache 2.0; DPDK and F-Stack are BSD. The engine links to them; none is modified

Four names come up throughout the deck, so here is what each one is. Chronicle Queue is the on-disk journal. Aeron is how a copy of that journal reaches another host. DPDK is how a program takes a network card away from the operating system, and F-Stack is the TCP that runs on top of it, so the engine still talks sockets. The first two are in every deployment; the last two are an optional transport.

Read it top down. The application registers listeners. A protocol engine owns the codec and the session state machine. Under them, one network event loop runs each connection's ring buffer on a single pinned thread, and the persistence layer journals every message before it leaves. The transport seam is where the kernel socket path and the DPDK path meet the same loop. Admin and metrics sit beside the hot path, never in it.

Six design decisions, each made for a measured reason

One spinning thread per loop

A blocking read pays a 5 to 20 µs kernel wake-up that varies run to run. Spinning removes it. The price is one core per loop.

Pinned to an isolated core

Ticks, interrupts and other threads are moved off the core at boot. Little at the median, a lot at the tail, and it makes runs comparable.

Flyweights over direct buffers

A message is a view over the bytes where they arrived; fields are read and encoded in place. No parse tree, no copies, no objects.

Lock-free ring per connection

Any thread claims, encodes and commits; the loop drains to the socket. A commit from the loop thread is written at once.

Zero allocation, enforced by tests

A test asserts 0 bytes per order on the acceptor with the journal on, and at most 320 on the simulator. GC is a non-event.

Journal first, on the critical path

Durability before the send was never traded away. The work went into making the write cheap: 0.4 to 0.8 µs, page faults taken ahead.

Also: HOCON configuration with a component lifecycle (initialize, active, standby, stop), so latency-sensitive deployments can switch off admin, persistence or the scheduler

These are the reasons the engine is shaped the way it is. Each one was chosen against a measurement rather than a preference. The first two are about the host and are where the tail latency went. The middle two are about memory and are where the median went. The last two are the principles that were not negotiable: no garbage, and no send before the journal.

The order is sent from the loop thread, so stages 1 to 5 run back to back with no hand-off. The socket write is the largest fixed cost: 2.5 µs per message on the kernel, 0.76 on F-Stack. The journal writes cost 0.4 to 0.8 µs each after the page-fault fix.

On receive, up to 2,048 bytes are read in one call, the flyweight is pointed at them, sequence and session state are checked, the bytes are journaled, and the handler writes the ExecutionReport through the same five send stages. No object is created on either side.

Persistence: every message on disk before it is sent, under a microsecond per write

What is stored

One Chronicle Queue stream per session: an append-only memory-mapped file, daily rolling, found again at startup. Each entry: timestamp, direction, sequence number, raw bytes.

What it is for

ResendRequests are answered from the journal with PossDup set. On restart, sequence numbers come back from the latest entries. Replay by sequence or by time.

Tooling on the journal

A log viewer, a validator that compares local and remote copies entry by entry, and an MCP server so an assistant can query messages and session status.

The page-fault finding

The first write to each 4 KB page of the mapped file cost a 1 to 3 µs fault on the loop. A helper thread now faults 1 MB ahead: the write's p99.9 fell from 34 to 42 µs to 3 to 5, the round trip's max from 1,030 µs to 316.

Store type per session: Chronicle, plain memory-mapped, Aeron replication, or none.

Modules persistence and persistence-aeron; the pretouch thread is persistence.pretouch-ahead, default 1 MB

The journal is the part a risk officer cares about. Nothing leaves the engine before it is on disk, and the session can be rebuilt from the log. The engineering effort went into making that write cost less than a microsecond and allocate nothing. The page-fault story is a good example of the method: a stage timestamp showed a tail on the write, the cause was in how the file was mapped, and a background thread removed it without touching the format. Inbound messages are logged on receive, outbound at drain with the sequence number read from the ring. Logging and tracing are separate per-session switches.

Why it costs nothing

An encode and a copy into a shared buffer. Removing the publish changed the round trip by under 0.5 µs up to p99.99.

How gaps are closed

On start or activation the store asks each engine for entries after its last position; the engine replays them off the hot path.

What operations gets

Full session history off the trading host, a validator proving both copies match, and the MCP server reading from it.

Module persistence-aeron; reads are always served from the local copy; replay from the remote store back to an engine exists in the API

Every write goes to the local Chronicle journal first and synchronously, then the same bytes are published over Aeron to a store on another host. The engine's round trip does not see the publish, which we verified by removing it. If the store falls behind or restarts, it asks each engine for the entries it is missing and the engine replays them from its local journal off the hot path. The result is a full copy of every session's history on a host that is not in the trading path.

The latency programme

Every number in this deck comes from one repeatable measurement on a fresh AWS stack

One scripted run

Provision, deploy, 20,000 warm-up then 100,000 timed orders at 1,000 per second, record, destroy. Both engines journaling.

Honest timing

Clocked from the intended send, so a late sender cannot hide queueing. The sender's slip is recorded beside it.

A network baseline

sockperf measures the raw kernel TCP round trip between the same hosts in the same run.

Host checks

Each loop thread is sampled during the run: on its core, spinning, isolated, no interrupts, preemptions counted. A failed check fails the run.

Stage timestamps

An optional mode stamps every engine stage on both sides. It costs about 1.5 µs, so headline runs leave it off.

A permanent record

Every run appends one line to a history file in the repository: commit, host, options, percentiles. 56 runs to date.

One way leads

Headline figures are one way, marked ≈: half the measured round trip. What is measured is the round trip, an order out of the initiator to its acknowledgement back, timed on one clock, so no clock synchronisation is involved; it sits in grey or in brackets beside each one-way figure.

One command runs the whole cycle; the same script measured every milestone in this deck; change one thing, judge it on one stack

Before the numbers, the method. Everything was measured the same way on throwaway AWS stacks with the host state verified during the run, the sender's own lateness corrected for, and a raw network baseline alongside. Two stacks of the same type can differ by several microseconds, so the firmest evidence is always an A/B on one stack minutes apart. That discipline is what lets us say which change did what.

TCP stack, ≈ 5.6 µs

FreeBSD's TCP running in userspace on DPDK: about 2.8 µs per send or receive, two of each per round trip. A purpose-built stack would do each in well under a microsecond. This is the largest remaining software cost.

Engines, ≈ 3.7 µs

Decode, session logic, journal write, encode and socket call on both sides, with no allocation. The socket write itself is 0.76 µs on F-Stack against 2.5 on the kernel. Scales with clock: ≈ 2.1 µs at 5 GHz (4.1 per round trip).

Source: docs/latency-baseline.md, "where F-Stack's time goes", 26 October 2026; one way is half the measured round trip

The point for a buyer: the engine is not the bottleneck. On this host the two engines together account for about three and a half microseconds of a twenty-one microsecond one-way latency, seven and a half of a forty-one microsecond round trip. The rest is the network card and fabric, which only a different host changes, and the TCP stack, which is the next engineering target.

The transport seam: the kernel became one option and a userspace TCP stack the other

Event loop, sessions, handlers

unchanged above the seam

Transport and Endpoint interfaces: network.transport = kernel | fstack

NioTransport

Java NIO sockets and selector

FstackTransport

F-Stack via a C shim and JDK 25 FFM

Linux kernel TCP, ENA driver

FreeBSD TCP on DPDK, NIC owned

What it is

Two small interfaces under the event loop. The F-Stack one runs FreeBSD's TCP as a library on DPDK: one pinned thread polls the NIC, runs TCP, and runs the engine's loop iteration as the stack's callback.

What it bought

On c6in.2xlarge, ≈ 20.0 one way against 22.9 at p50 and 23.4 against 31 at p99 (40.0 / 45.8 and 46.7 / 62.1 round trip): the kernel's 12 µs p90-to-p99 band became 4. On AMD metal, ≈ 13.8 (27.6).

What it costs

A dedicated NIC and a core per process, root for the device mapping, a native build on the host, no TLS on that path. An option, not a requirement.

Module network-dpdk; the seam is in the network module; the kernel implementation wraps NIO one to one and measured no cost

The one architectural change of the programme. The engine did not know what a socket was beyond Java NIO. We put two small interfaces underneath it, kept the NIO implementation as the default, and added a second implementation on F-Stack, which is FreeBSD's TCP running in userspace on DPDK. Everything above the seam, sessions and handlers, is untouched. The buyer's takeaway: the kernel-bypass path is a configuration switch, with known costs, on an engine that is already fast on the kernel.

What is next: the remaining microseconds are in the TCP stack and the host, not the engine

A purpose-built TCP for the bypass path

F-Stack's FreeBSD TCP costs ≈ 3 to 5.5 µs one way (6 to 11 per round trip). Published from-scratch stacks run at a few hundred nanoseconds per packet. A minimal single-connection stack is the largest software win left: up to ≈ 4.5 µs one way on c6in.

Metal with the fast card, repeated

One AMD metal stack gave ≈ 13.8 µs one way (27.6 round trip). A c6in.metal run would separate the hypervisor's share from the card generation's on the Intel path; both are an afternoon and under $30.

Write-combining for the NIC's low-latency queue

The kernel driver uses it; the DPDK path never did because the stock vfio driver has none. Enabling it would move every bypass row down together.

Hardening the bypass path for production

Graceful stack shutdown, running without root, TLS on the bypass transport, and the alert and dashboard metric names reconciled with what the engine emits.

Everything above is optional for a kernel-path deployment, which is production-ready today at ≈ 23 µs one way (45 round trip) on a cloud VM and ≈ 17 to 19 (34 to 38) on metal

The engine's own share is four to seven microseconds and tracks the clock, so the next gains are elsewhere. The biggest is a TCP stack written for one connection on a reliable link, which the literature says runs an order of magnitude cheaper than FreeBSD's. The rest is host work and the production hardening a bypass deployment needs.
